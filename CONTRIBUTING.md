# Contributing to GitLab Self-Hosted

Thank you for contributing. By participating, you agree to follow the [Code of Conduct](CODE_OF_CONDUCT.md).

## Ways to contribute

- Report reproducible bugs or documentation problems.
- Suggest focused improvements to GitLab workflows.
- Improve tests, error handling, localization, or packaging.
- Review issues and pull requests constructively.

Do not include GitLab tokens, cookies, private repository contents, customer data, or other secrets in issues, pull requests, tests, or logs.

## Development setup

Python 3.9 or later is required. The runtime has no Python package dependencies; `glab` is the recommended optional authentication backend. Tests and coverage use the pinned development dependency.

```bash
git clone https://github.com/Euraika-Labs/gitlab-selfhosted.git
cd gitlab-selfhosted
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt
.venv/bin/python -m coverage run --source=skills -m unittest discover -s tests -v
.venv/bin/python -m coverage xml -o coverage.xml
python3 scripts/build_plugin.py
```

The build creates a versioned ZIP and checksum under `dist/`. Do not commit generated files from `dist/` or Python bytecode caches.

## Making changes

1. Open an issue for substantial changes so the scope can be discussed first.
2. Create a focused branch from `main`.
3. Keep the plugin dependency-free unless a dependency is clearly justified.
4. Add or update tests for behavior changes.
5. Update documentation and localized interface copy when needed.
6. Run the full test suite and package build before submitting.
7. Open a pull request with a clear description of behavior, verification, and any risks.

## Safety requirements

- Read operations must not change GitLab state.
- Creating issues or merge requests and retrying or canceling pipelines must remain behind explicit user confirmation and the `--confirm` safeguard.
- Prefer authentication through `glab` and its operating-system credential store. Direct fallback tokens may only be read from `GITLAB_TOKEN`; never accept them in URLs, command arguments, source files, or logs.
- Do not weaken URL validation, TLS verification, output redaction, or error handling without a documented security reason.
- New API operations should return compact JSON and avoid unnecessary data collection.

## Versioning and releases

Use [Semantic Versioning](https://semver.org/). The version in `kimi.plugin.json`, release tag, and changelog entry should agree. Release artifacts must be generated by the CI build or the reproducible local packaging script.

## Reporting security issues

Follow [SECURITY.md](SECURITY.md) instead of opening a public issue for a suspected vulnerability.
